## 1. 엔티티 — 왜 빠졌고 무엇을 더할지

**왜 빠졌는가.** `docs/IMPLEMENTATION_PLAN.md` §1.5(:83)는 엔티티·개념·요약 페이지를 의도적으로 거부한다. 문서는 시스템 책임 단위로 나누고, 개념은 그 동작을 소유하는 문서 안에 둔다는 원칙이다. 이 원칙 자체는 유지할 가치가 있다. 문제는 §1.1 비교표에 데이터 모델·엔티티 축이 없어 '여러 책임에 걸치는 개념을 어디서 처음 찾는가'라는 질문이 설계에서 빠졌다는 점이다.

**실제 격차(crumbs-eval 산출물 기준).**

- 같은 개념을 문서마다 다른 표현으로 쓴다: `payment/overview.md:5` '재화A·재화B', `viewer/회차-결제-처리.md:15` '재화A N원', `payment/결제-시작.md:11` '원화 결제(원페이)'·'원페이'.
- 교차 개념의 진입점이 없다. '결제 트랜잭션'은 `### 원페이 결제 트랜잭션 시작`(스토어C-원페이-결제.md:58)·`### 결제 트랜잭션 롤백`(:64)·`### 결제 트랜잭션 키`(앱스토어-결제.md:42)로, '재화B 잔액'은 `### 재화B 잔액 부족`(스토어C-결제수단.md:53)으로 `grep '^### '`에 적중하지만 서로 다른 문서에 흩어져 있어 어느 것이 정의인지 알 수 없다. '회차 소유권'은 `###` 제목 어디에도 없다.
- `duplicate-policy` 규칙은 정책 제목 중복만 잡고 개념 정의의 중복은 잡지 못한다.

**기존 체계의 해법.** `docs/specs/product/용어집.md`는 `| 표준 용어 | 기획서 표현·별칭 | 탐색 정의 | 도메인 | 관련 SPEC |` 표 한 장으로 교차 개념의 진입점을 만든다(:34-47). 핵심은 :9의 경계다. 용어집은 "용어의 탐색 의미만 소유"하고 노출 문구·채널 정책·API 식별자는 책임 문서가 확정한다. 별칭 열은 기획서 표현('기다무'→'기다리면 무료')과 금지 표현('서랍(금지)'→'사이드메뉴', :43)까지 흡수해 grep 동의어 역할을 한다. 외부 기준도 같은 방향이다: arc42 §12 Glossary("ubiquitous language"), RFC 7322 §3.6 약어 첫 사용 전개, Anthropic memory 문서의 '한 파일 한 주제'.

**제안.** 엔티티 페이지 없음 원칙은 유지한다. 대신 `src/templates/ko.ts` overview 템플릿에 선택 절 `## 용어`를 더하고 형식을 한 줄로 고정한다.

```
- 표준 용어(별칭1, 별칭2) — [소유 상세 문서의 정책 제목](파일.md#정책-앵커)
```

정의 본문은 쓰지 않고 링크만 둔다. 그래서 책임 소유·중복 금지 원칙과 충돌하지 않고, 기존 `broken-anchor` 검사가 링크를 검증하므로 새 check 규칙은 필요 없다. `skills-ko.ts` writer '기존 코드 문서화' 6번에 "정책 이름·화면 이름에 기획서·코드가 다른 표현을 쓰면 개요의 용어 절에 별칭을 더한다"를, finder 1번 grep 안내에 "개요의 용어 절 별칭도 본다"를 추가한다.

**남은 결정.** 도메인 간 공통 개념(재화B 잔액, 회차 소유권)은 인덱스에 있어야 찾히지만 인덱스는 '도메인 목록만 유지'(IMPLEMENTATION_PLAN.md:1620) 원칙이 있다. 용어 절을 개요마다 둘지 인덱스에 한 번만 둘지는 사용자 확인이 필요하다.

## 3. API 계약을 한 곳에

**결론.** API 계약을 책임 도메인으로 다룬다. `<specDir>/api/` 아래 엔드포인트마다 상세 문서 하나를 일반 템플릿으로 쓴다.

| 일반 어휘 | api/ 상세 문서에서의 내용 |
|---|---|
| 목적 | 이 엔드포인트가 소유하는 계약 하나와 맡지 않는 범위(사용자 안내는 화면 문서) |
| 현재 동작 | 요청 필드, 응답 필드(타입·필수·nullable·의미), 응답·오류 코드 표, 정의되지 않은 응답 처리 |
| 정책 | 재시도·멱등성·인증·버전 |
| 근거 | 클라이언트 호출 경로(+rawDir의 API 원문) |
| 관련 문서 | 호출하는 화면 문서 역링크 |

공통 전송·세션 계약(헤더·인증·쿠키·재시도)은 `api/` 안의 상세 문서 하나에 한 번만 둔다. 정책 이름은 전역 유일 규칙 때문에 'HOME-145 머니 부족 응답'처럼 번호를 넣는다.

**소유 경계.** API 문서는 '서버가 무엇을 반환하고 각 코드가 무슨 뜻인가'를 소유한다. 화면(feature) 문서는 '각 코드에서 앱이 무엇을 보여 주는가'만 적고 API 문서로 링크한다. 같은 코드가 화면별로 다른 안내를 만들면 코드별 사용자 결과를 화면 문서에도 쓴다(기존 체계 템플릿 :128).

**참조 구조(기존 체계 `docs/specs/integration/api/`).**

## 7. 작업 절차

1. `docs/IMPLEMENTATION_PLAN.md`(특히 §1.1, §1.5, 6.3.2, :1519-1620), `src/templates/ko.ts`, `skills-ko.ts`, `agents.ts`, `src/headings.ts`, `src/rules/`, `src/check.ts`, 테스트 파일을 읽고 C13(두 사본 차이)을 먼저 확인한다.
2. 6절 표를 바탕으로 변경 계획을 사용자에게 먼저 제시한다. 결정이 필요한 항목을 명시적으로 묻는다: C1 용어 절 위치(개요 vs 인덱스), C3 headings override 여부, C9 심각도, C10 기록 저장 주체, C14 길이 상한. `[확인 필요]`가 남은 채 진행하려면 사용자의 명시적 승인을 받는다.
3. 사용자 확인 후 Haiku(`claude-haiku-5-5`) 하위 에이전트에게 구현을 맡긴다. 같은 파일을 두 에이전트가 동시에 고치지 않도록 나눈다: (a) `ko.ts` + `headings.ts`, (b) `skills-ko.ts` + IMPLEMENTATION_PLAN 6.3.2, (c) `section-order.ts` + `check.ts` + 테스트. README 예시는 마지막에 순서대로.
4. 검증: `npm test` 통과, 임시 디렉터리에서 `npx crumbs-spec init` 후 `npx crumbs-spec check`가 통과하는지 확인한다(템플릿을 그대로 복사한 문서가 section-order를 통과해야 한다). C5 적용 후 open-question 집계·로그 기대값 테스트가 바뀌지 않는지 확인한다.
5. 결과(diff 요약, 테스트 출력, 남은 `[확인 필요]`)를 한국어로 보고한다. git commit·push는 하지 않는다.
