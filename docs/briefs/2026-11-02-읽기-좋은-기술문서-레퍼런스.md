# 사람이 읽기 좋은 기술 문서 — Markdown 기준 레퍼런스 (2026-11-02)

## 이 문서의 범위와 읽는 법

이 문서는 사람이 읽기 좋은 산문과 기술 문서의 기준을 모은 레퍼런스다. 대상은 Markdown으로 쓰는 스펙, 설계 문서, README, ADR, RFC다. 기준은 모두 공개된 표준, 스타일 가이드, 책, 연구에서 가져왔다. 특정 조직의 내부 문서나 저장소는 기준으로 삼지 않았다.

모든 기준에는 검사 방법 태그를 붙였다.

- 린터: markdownlint, Vale, textlint, hanlint 같은 도구가 규칙 이름으로 바로 잡아낸다.
- 스크립트: 정규식이나 단어 수 집계 같은 짧은 스크립트로 근사 검출할 수 있다.
- 사람: 의미, 적합성, 독자 관점은 사람이 읽고 판단한다.

출처에는 검증 상태를 표시했다.

- 확인: 원문을 열어 인용과 위치를 대조했다.
- 교정: 원문을 열었고, 처음 수집한 쪽 번호나 절 이름을 바로잡아 반영했다.
- 미확인: 원문을 열 수 없었다. 미확인 자료는 인용하지 않고 서지만 적었다.
- (책)은 단행본에서, (연구)는 동료 심사 논문이나 실험 데이터에서 나온 기준이다.

인용은 출처마다 한 구절만, 15단어 이내로 큰따옴표에 넣었다. 이 문서의 소스는 Ciro Santilli가 구분한 두 프로필 가운데 writability 프로필(줄바꿈 없음, 하이픈 목록, 펜스 코드)을 따른다. 따라서 줄 길이 규칙 MD013은 이 문서에 적용하지 않고, 한 문장 한 줄 방식은 선택지로 본문에서 소개한다.

## 핵심 원칙 10가지

여러 출처가 반복해서 요구하는 열 가지 원칙이다.

1. 독자가 누구이고 무엇을 하려는지 먼저 정한다. (Google Technical Writing One; ISO 24495-1)
2. 가장 중요한 내용을 맨 앞에 둔다. (Nielsen 1997; GOV.UK)
3. 한 문장에 생각 하나, 한 단락에 주제 하나만 담는다. (Federal Plain Language Guidelines; ASD-STE100)
4. 뺄 수 있는 단어는 뺀다. (Strunk (책); Orwell)
5. 능동태로 행위 주체를 드러낸다. (Google Technical Writing One; 법제처 정비기준)
6. 제목은 홀로 읽혀야 하고 레벨을 건너뛰지 않는다. (WCAG 2.2; W3C WAI)
7. 문서 유형을 하나로 정하고 한 문서에 섞지 않는다. (Diátaxis; DITA)
8. 같은 개념에는 같은 용어를 쓰고 약어는 첫 사용에서 풀어 쓴다. (RFC 7322; Google 스타일 가이드)
9. 링크 텍스트는 목적지를 설명한다. (Google Markdown style guide; markdownlint MD059)
10. 점수와 린터는 보조 지표다. 최종 판단은 사람이 한다. (DuBay (연구); Gopen & Swan (연구))

## 문장

Strunk는 간결함을 첫 덕목으로 꼽았다. "Vigorous writing is concise." (William Strunk Jr., The Elements of Style, 1918) (책) Zinsser는 군더더기를 "the disease of American writing"이라 불렀다. (William Zinsser, On Writing Well, NYSBA 기사 인용) (책) 짧은 문장 자체가 목표는 아니다. Williams는 "there is nothing wrong with a long sentence if its subjects and verbs match"라고 썼다. (Joseph M. Williams, Michigan Bar Journal 1992) (책)

| 기준 | 근거 출처 | 검사 방법 |
| --- | --- | --- |
| 한 문장에 생각 하나만 담는다 | Federal Plain Language Guidelines "Express only one idea in each sentence."; Google Technical Writing One | 사람 |
| 영문 문장은 25단어를 넘기지 않는다 | GOV.UK "Try to split up sentences that are over 25 words long."; ASD-STE100은 절차 20단어, 설명 25단어 | 린터: Vale `Microsoft.SentenceLength`(기본 30, 25로 조정), textlint `sentence-length` |
| 한국어 문장은 한두 가지 정보만 담는다 | 국립국어원 행정문서 표현 개선 보고서(연구) "되도록 한 문장에는 한두 가지의 정보만 담아 제시한다."; 공공언어 바로 쓰기 | 스크립트: 글자 수·연결어미 개수 임계값은 팀이 정한다 |
| 기능 없는 단어를 지운다 | Strunk Rule 13(책); Orwell "If it is possible to cut a word out, always cut it out." | 린터: `write-good.TooWordy`, `proselint.Needless` |
| 능동태를 기본으로 쓴다 | Strunk Rule 10(책); Google Technical Writing One; 법제처 정비기준 | 린터: `write-good.Passive`(영문), hanlint 이중 피동(한국어) |
| 주어 뒤에 동사를 빨리 둔다 | Gopen & Swan(연구) "Follow a grammatical subject as soon as possible with its verb." | 사람 |
| 새 정보는 문장 끝에 둔다 | Gopen & Swan stress position(연구); Strunk Rule 18(책) | 사람 |
| 행위자를 주어로 세우고 명사화를 피한다 | Williams(책); Purdue OWL Paramedic Method "Draw a box around the \"is\" verb forms"; Plain Language hidden verbs | 린터 근사: `write-good.E-Prime`, `write-good.ThereIs`; 판정은 사람 |
| 짧은 단어로 충분하면 긴 단어를 쓰지 않는다 | Orwell Rule (ii) | 린터: `Microsoft.ComplexWords` |
| 현재 시제를 기본으로 쓴다 | Federal Plain Language Guidelines; Microsoft Korean Style Guide 4.1.12; 카카오디벨로퍼스 가이드 | 린터: Vale existence(곧, 아마, 예정, 향후) |
| 이중 부정을 긍정문으로 바꾼다 | 법제처 정비기준; 카카오엔터프라이즈 10계명(2차 기사) | 사람; 정규식 보조 |
| 소스에서는 한 문장을 한 줄에 쓴다 | Brandon Rhodes가 인용한 Kernighan "Start each sentence on a new line."; SemBr; GitLab | 스크립트 근사; 렌더 결과는 바뀌지 않아야 한다 |

Gopen & Swan은 이 원칙들이 규칙이 아니라 독자 기대라고 못 박았다. (연구) 대부분 지키고, 의도적으로 깨는 곳만 예외로 둔다.

## 단락과 절

단락은 주제문으로 시작한다. Strunk Rule 9는 단락마다 주제문으로 시작하고 끝을 시작과 호응하게 맺으라고 했다. (책) Google Technical Writing One도 첫 문장이 단락의 요지를 말하게 한다. Nielsen은 단락마다 생각 하나만 담으라고 했다. (연구)

단락 길이 기준은 출처마다 다르지만 범위가 겹친다.

| 출처 | 문장 수 상한 | 추가 기준 |
| --- | --- | --- |
| Federal Plain Language Guidelines | 3~8문장 | 150단어 이내, 250단어 초과 금지 |
| GOV.UK | 5문장 | 없음 |
| Google Technical Writing One | 3~5문장 권장, 7문장 초과 회피 | 첫 문장이 요지 |
| Microsoft Writing Style Guide | 없음 | "Three to seven lines is about the right length for a paragraph." 한 줄 단락 허용 |
| ASD-STE100(Wikipedia 요약) | 6문장 | 단락당 주제 하나 |
| 카카오디벨로퍼스 가이드 | 5문장 | "한 문단은 세 줄 이하, 다섯 문장 이내로 작성합니다." |

단락 안에서는 익숙한 정보로 시작하고 새 정보로 끝낸다. 이 원칙은 Williams & Bizup의 12판 내용을 2차 요약으로만 확인했다. (책, 원문 미열람) Gopen & Swan은 앞 문장과 이어 주는 정보를 문장 앞 topic position에 두라고 했다. (연구) 설명에는 예시를 붙인다. Pinker는 "an explanation without an example is little better than no explanation at all"이라고 썼다. (Steven Pinker, Chronicle Review 2014, 전재본 확인) (책)

절은 하나의 질문에 답하는 단위다. DITA는 토픽을 "short enough to be specific to a single subject or answer a single question"으로 정의한다. (OASIS DITA 1.0) Information Mapping은 정보를 작은 단위로 나누고 단위마다 라벨을 붙인다. "Each group has a clear label." (TechScribe 요약, 2020) WCAG 2.2 SC 2.4.10은 긴 본문을 절 제목으로 나누라고 요구한다. Hartley & Trueman의 17개 실험은 "headings in either form aided the recall, search and retrieval of information"을 보였다. (연구) Red Hat은 모듈마다 제목 바로 아래 50~300자의 짧은 설명을 두라고 한다. Rust RFC 템플릿은 Summary를 한 단락으로 제한한다. Standard Readme는 제목 아래 한 줄 설명을 요구한다. "Must be less than 120 characters."

## 제목과 구조

제목 규칙은 출처가 가장 많이 겹치는 영역이다.

- H1은 문서에 하나만 둔다. Google 스타일 가이드는 "only use a level-1 heading once on a page"라고 썼다. Microsoft Learn도 같다.
- 레벨을 건너뛰지 않는다. W3C WAI는 "Skipping heading ranks can be confusing and should be avoided where possible"이라고 했다. Ciro Santilli의 Markdown Style Guide도 "Don't skip header levels."라고 적었다.
- 제목은 홀로 읽혀야 한다. WCAG 2.2 SC 2.4.6은 "Headings and labels describe topic or purpose."를 요구한다. 'Introduction', 'Overview', '기타' 같은 범용 제목은 GOV.UK, Red Hat, GitLab이 모두 피하라고 한다.
- 정보량이 큰 단어로 시작한다. Pernice의 F자 패턴 연구는 첫 두 단어로 요지가 전달되게 하라고 했다. (연구) 길이는 Red Hat 기준 "Keep headings between 3 and 11 words", GitLab 기준 70자 이내다.
- 작업 제목은 동사로, 개념 제목은 명사구로 쓴다. Google 스타일 가이드, Red Hat, GitLab task 유형이 일치한다. GitLab은 '능동 동사 + 명사'(Create an issue) 형식을 쓴다.
- 질문형과 진술형을 한 문서에 섞지 않는다. Hartley & Trueman은 두 형태의 효과 차이가 없다고 보고했으므로 기준은 일관성이다. (연구)
- 제목 끝에 마침표나 콜론을 쓰지 않고 제목에 링크를 넣지 않는다. (Microsoft Writing Style Guide; markdownlint MD026; GitLab)
- 같은 레벨의 제목은 고유해야 한다. GitHub Docs는 "Each header at the same level on a page must be unique."라고 썼다. 제목과 하위 제목 사이에는 본문이 있어야 한다.

문서 구조는 독자가 훑어 읽는다는 전제에서 정한다. Nielsen은 "People rarely read Web pages word by word"라고 보고했다. 79%가 새 페이지를 스캔했다. (연구) Pernice는 "Include the most important points in the first two paragraphs."라고 권고했다. (연구) Gopen & Swan은 새 주장 앞에 맥락을 먼저 두라고 했다. (연구) Google Technical Writing One은 문서 첫머리에 범위, 비범위, 대상 독자를 명시하게 한다. Mark Baker는 "There is no first, last, previous, next, up, or back anymore."라고 썼다. 모든 문서는 혼자 읽혀야 한다. (책, 본문 미열람) Carroll의 미니멀리즘은 "Allow learners to start immediately on meaningful tasks."를 첫 원칙으로 둔다. 배경을 길게 앞세우지 않는다. (InstructionalDesign.org 요약)

문서 유형은 Diátaxis의 네 유형 중 하나로 정한다. "How-to guides must be written from the perspective of the user, not of the machinery." (Daniele Procida, Diátaxis) Django는 "Reference guides aren't the place for general explanation."이라고 썼다. The Good Docs Project는 "Address one logical goal (task) per how-to page."를 요구한다.

| 문서 유형 | 절 순서 | 출처 |
| --- | --- | --- |
| README | Title(저장소 이름과 일치) → Short Description → Table of Contents(100줄 초과 시) → Install(코드 블록) → Usage(코드 블록) → Contributing → License(마지막) | Standard Readme spec |
| README | 프로젝트 이름 → 설명(무엇을 하고 왜 중요한지) → 대상 사용자 → 의존성 → 사용 방법 → 기여 → 추가 문서 → 도움 받는 방법 → 이용 약관 | The Good Docs Project |
| 설계 문서 | Context and scope → Goals and non-goals → 설계 본문 → Alternatives considered | Design Docs at Google(Ubl, 개인 글) |
| 기능 스펙 | 저자 1명 명시, Scenarios, Nongoals, Open Issues(코딩 전 비움) 포함 | Spolsky, Painless Functional Specifications |
| ADR | Title → Context → Decision → Status → Consequences, 1~2쪽 | Nygard 2011 |
| ADR | 제목 → Context and Problem Statement → Considered Options → Decision Outcome, 선택 절로 Decision Drivers·Consequences·Confirmation·Pros and Cons | MADR 4.x(필수 표기는 없고 optional 표시 없는 절을 핵심으로 본다) |
| RFC | Summary(한 단락) → Guide-level explanation → Reference-level explanation → Drawbacks → Rationale and alternatives → Unresolved questions | Rust RFC template(확인한 절만 적음) |
| RFC | Abstract(인용 없음) → Introduction(첫 절) → 본론 → Security Considerations → References | RFC 7322 |
| 작업 토픽 | prereq → context → steps → result → example → postreq(모두 선택) | OASIS DITA 1.2 taskbody |
| 작업 문서 | 제목(동사 + 명사) → 도입 → `Prerequisites:` 목록 → 콜론으로 끝나는 리드인 → 번호 단계(위치 → 동작) → 다음 단계 | GitLab topic types |

Spolsky는 "Your specs should be owned and written by one person."이라고 했다. Ubl은 설계 문서의 Context 절에 대해 "This isn't a requirements doc. Keep it succinct!"라고 썼다. Nygard는 ADR 분량을 "The whole document should be one or two pages long."으로 제한했다. Rust RFC의 Drawbacks 절은 "Why should we *not* do this?"에 답해야 한다. DORA 2021은 문서마다 소유자를 두라고 했다. "Define owners." (Google Cloud DORA, State of DevOps 2021) (연구)

## 목록·표·도식·코드

목록과 표 중 무엇을 쓸지 먼저 정한다. Google Markdown style guide는 "Avoid using tables when your data could easily be presented in a list."라고 썼다. Google 스타일 가이드는 항목마다 관련 데이터가 세 개 이상일 때만 표를 쓰고, 열이 하나면 목록으로 바꾸게 한다. GitHub Docs와 GitLab도 단순 목록에 표를 쓰지 않는다. 목록 규칙은 다음과 같다.

- 순서가 있으면 번호 목록, 없으면 글머리 목록을 쓴다. (Google Technical Writing One)
- 항목이 하나뿐인 목록은 만들지 않고, 항목은 같은 문법 구조로 쓴다. Strunk Rule 15는 대등한 생각을 같은 형태로 나열하라고 했다. (Google 스타일 가이드; 행정업무운영 편람 부록; Strunk (책))
- 목록 앞에는 도입 문장을 둔다. 바로 이어지면 콜론으로 끝낸다. (Google 스타일 가이드)
- 절차는 한 단계에 한 동작만 쓰고 명령형으로 시작하며, 동작보다 위치를 먼저 말한다. (Google; Microsoft; The Good Docs Project)
- 선택 단계는 'Optional:' 접두어를 붙이고, 여러 방법이 있으면 기본 방법만 문서화한다. (Google; GitLab)

표 규칙은 다음과 같다.

- 헤더 행과 구분 행을 반드시 둔다. GFM은 표를 "consisting of a single header row, a delimiter row separating the header from the data"로 정의한다.
- 모든 행의 열 수를 헤더와 맞춘다. markdownlint MD056의 근거는 "Extra cells in a row are usually not shown, so their data is lost."다.
- 빈 셀을 두지 않는다. GitLab은 `None`, 카카오디벨로퍼스는 `-`로 채운다. GitHub Docs는 모든 셀에 값을 요구한다.
- 셀을 병합하지 않고 번호 절차 중간에 표를 넣지 않으며, 표 헤더는 문장식 대소문자로 쓴다. (Google 스타일 가이드; GitLab)
- HTML 표와 레이아웃용 표를 쓰지 않는다. Microsoft Learn은 소스 가독성을 Markdown의 핵심 원칙으로 본다. (Microsoft Learn; W3C WAI Tables)

도식 규칙은 C4 model과 접근성 가이드에서 가져왔다.

- 모든 도식에 종류와 범위를 알리는 제목을 붙인다. Mermaid라면 `title` 지시어나 직전 캡션을 쓴다. (C4 model)
- 표기 범례를 두고 색만으로 의미를 구분하지 않는다. GitLab은 도형으로만 구분하고 Mermaid 선언 직후 `accTitle`과 `accDescr`를 넣게 한다.
- 선은 한 방향만 나타내고 구체적 라벨을 붙인다. "Every line should represent a unidirectional relationship." (Simon Brown, C4 model)
- 텍스트, 코드, 터미널 출력을 이미지로 넣지 않는다. (Google 스타일 가이드 접근성)
- 모든 이미지에 alt 텍스트를 넣고 장식 이미지는 빈 alt를 쓴다. GitHub Docs는 40~150자, GitLab은 155자 이하를 권하며 파일명을 alt로 복사하지 않는다. (Microsoft Learn; W3C WAI alt Decision Tree)

코드 규칙은 다음과 같다.

- 펜스 코드 블록을 쓰고 언어를 항상 지정한다. (Google Markdown style guide; Ciro Santilli; Django)
- 코드 블록은 문장으로 소개하고 한 줄은 80자 안에서 줄바꿈한다. 생략 부분은 `...`가 아니라 해당 언어의 주석으로 표시한다. (Google 스타일 가이드)
- 코드 블록 하나에 명령 하나만 넣고 출력은 별도 블록으로 나눈다. 출력 없이 `$`만 붙이지 않는다. (Red Hat; remark-lint `no-shell-dollars`)
- API 정의나 DB 스키마를 통째로 복사해 넣지 않는다. 필요한 부분만 요약하고 원본을 링크한다. (Design Docs at Google)

알림(Note, Tip, Warning) 규칙은 모든 출처가 '절제'로 모인다.

- 본문 흐름 밖의 부가 정보에만 쓴다. 전제조건, 절차 단계, 꼭 알아야 할 정보는 알림으로 쓰지 않는다. (Google 스타일 가이드)
- 연속으로 두지 않고 한 절에 둘 이상 두지 않는다. 절을 알림으로 시작하지 않고 알림 안에 절차를 넣지 않는다. (Google; GitLab; GitHub Docs; Red Hat)
- 문서당 1~2개로 제한한다. "If you need to use alerts, limit them to one or two per article." (Microsoft Learn) Warning은 폐기나 데이터 손실 가능성에만 쓴다. (GitLab)

## 링크와 탐색

링크 텍스트는 목적지를 설명해야 한다. markdownlint MD059는 `click here`, `here`, `link`, `more`를 기본 금지 텍스트로 둔다. 근거는 스크린리더가 링크를 맥락 없이 읽는다는 점이다. Google 스타일 가이드는 대상 페이지 제목이나 고유한 설명 구절을 쓰고, 같은 페이지에서 다른 대상에 같은 링크 텍스트를 재사용하지 않게 한다. GitHub Docs는 대상 문서 제목을 그대로 링크 텍스트로 쓰고, 같은 글에서 같은 링크를 반복하지 않는다. GitLab의 표준 문형은 'For more information, see [link text](link.md).'다.

- URL을 본문에 그대로 적지 않는다. GFM 자동 링크는 인식 조건이 좁고 설명이 없다. (markdownlint MD034; remark-lint `no-literal-urls`)
- `#fragment` 링크는 실제 제목 앵커와 일치해야 한다. (markdownlint MD051) 중복 제목은 앵커를 깨뜨린다. (MD024)
- 링크는 한 줄에 전부 쓰고 제목 안에 넣지 않으며, 한 페이지에서 다른 페이지로 가는 링크는 15개 이하로 둔다. (GitLab)
- 'above', 'below' 같은 방향 표현과 '위에서 설명한 대로' 같은 순서 의존 표현을 피한다. 각 절은 자체 완결적이어야 한다. (Google 스타일 가이드; Carroll 미니멀리즘 원칙 4; Every Page is Page One)
- 절 단위로 직접 링크할 수 있는 주소를 제공한다. Write the Docs는 이를 Addressable이라 부른다.

인덱스와 README가 진입점이다. Google Markdown style guide의 문서 레이아웃은 H1 → 짧은 소개 → `[TOC]` → H2 주제들 → 'See also' 순서다. Standard Readme는 100줄이 넘는 README에 모든 절로 링크하는 목차를 요구한다. Microsoft Writing Style Guide는 긴 문서에 목차와 '맨 위로' 링크를 두게 한다. DORA 2021은 문서가 찾을 수 있고 잘 조직되어야 한다고 측정한다. (연구) Write the Docs는 선행 개념이 먼저 오는 순서를 Cumulative 원칙으로 두고, "Structure content to help readers identify and skip over concepts."를 Skimmable 원칙으로 둔다.

ADR 파일은 `doc/arch/adr-NNN.md`처럼 일련번호로 저장하고 번호를 재사용하지 않는다. 번복된 결정은 Status를 superseded로 바꾸고 대체 ADR을 링크한다. (Nygard) MADR 파일명은 `NNNN-title-with-dashes.md`이고 `decisions/` 폴더에 둔다.

## 용어와 어조

같은 개념에는 같은 용어를 쓴다. Google 스타일 가이드 번역 절은 같은 개념에 항상 같은 용어와 표기를 쓰라고 한다. RFC 7322는 "Capitalization must be consistent within the document."라고 썼다. Write the Docs의 Consistent 원칙과 markdownlint MD044(고유명사 대소문자)가 같은 기준이다. 용어 기준은 대상 독자를 정한 뒤 용어집으로 관리한다. Bailin & Grafstein은 단어 목록이 독자 집단의 균질성을 전제한다고 비판했다. (연구, 서평으로 확인)

약어는 첫 사용에서 풀어 쓴다.

- RFC 7322 §3.6은 제목과 본문 첫 등장에서 약어를 풀어 쓰게 한다. TCP, HTTP처럼 널리 알려진 것만 예외다. WCAG 2.2 SC 3.1.4도 풀어 쓴 형태를 확인할 수단을 요구한다.
- Federal Plain Language Guidelines는 문서당 약어를 3개 이하, 가급적 2개로 제한한다. 행정 효율과 협업 촉진에 관한 규정 제7조 제2항은 일반화되지 않은 약어와 전문용어를 피하게 한다.
- Pinker는 약어가 필자의 몇 초를 아끼고 독자의 몇 분을 빼앗는다고 했다. (책)

전문용어는 독자 기준으로 점검한다. Pinker는 지식의 저주를 경계하라고 했다. 자신이 아는 것을 독자가 모른다는 사실을 상상하기 어렵다. (책) Orwell Rule (v)는 일상어가 있으면 외래어와 전문용어를 쓰지 말라고 했다. 법제처 정비기준은 '어렵다'의 기준을 일반 국민의 눈높이로 둔다.

어조 규칙은 다음과 같다.

- 독자를 2인칭 'you'로 부른다. 'we'와 'the user'를 피한다. (Google 스타일 가이드; GitLab)
- 'just', 'simply', 'easy', 'quickly', 'please', 'in order to', 'leverage'를 쓰지 않는다. (Google word list; Django; GitLab)
- 느낌표, 'let's' 어투, 'Please note' 같은 상투구, 'You can'으로 반복되는 문장 시작을 피한다. (Google 스타일 가이드 어조) 상투어와 비유는 Orwell Rule (i)와 `proselint.Cliches`가 같다.
- 'This page explains', 'This topic covers' 같은 자기참조 문구를 쓰지 않는다. (GitLab; Red Hat)
- 메타 담화, 자기 변명, 과도한 한정어를 뺀다. Pinker는 이를 고전적 문체라 부른다. (책) 린터로는 `proselint.Hedging`, `write-good.Weasel`이 잡는다.
- 제품 문서에서는 축약형을 피하고 비용이나 향후 릴리스 약속을 쓰지 않는다. (Red Hat)

편향 없는 표현은 Microsoft와 Red Hat 기준을 따른다.

- 일반 지칭에 he/she를 쓰지 않고 2인칭, 복수형, 역할명, 단수 they로 바꾼다. 장애는 관련 있을 때만 사람 중심으로 언급한다. (Microsoft; Django)
- master/slave는 primary/subordinate, DMZ는 perimeter network로 바꾼다. (Microsoft) blacklist/whitelist는 blocklist/allowlist로 바꾼다. (Red Hat)
- 린터로는 `Microsoft.GenderBias`, alex 패키지(`alex.Ablist`, `alex.Condescending`, `alex.Gendered`)가 잡는다.

요구 수준 키워드는 BCP 14를 따른다. RFC 8174는 MUST, SHOULD, MAY가 "only when they are in all capitals" 정의된 의미를 가진다고 명시한다. RFC 2119 §6은 이 키워드를 "must be used with care and sparingly" 쓰라고 했다. 대문자 키워드를 쓰는 문서는 앞에 BCP 14 보일러플레이트를 둔다. 소문자 must와 대문자 MUST의 혼용은 정규식으로 검출한다.

## 한국어 기술 문서 특수 기준

상위 원칙은 국어기본법 제14조다. 현행 법률 제20491호(시행 2025. 4. 23.) 제14조 제1항은 "공공기관등은 공문서등을 일반 국민이 알기 쉬운 용어와 문장으로 써야 하며"라고 규정한다. 행정 효율과 협업 촉진에 관한 규정 제7조는 "문서는 「국어기본법」 제3조제3호에 따른 어문규범에 맞게 한글로 작성하되" 뜻 전달에 필요하면 괄호 안에 한자나 외국어를 쓰게 한다. 법제처 정비기준은 쉬움의 기준을 이렇게 둔다. "이때 ‘어렵다’는 기준은 법률 전문가의 관점이 아닌, 일반 국민의 눈높이가 되어야 한다."

문체는 문서 유형별로 하나만 정한다.

- Microsoft Korean Style Guide는 일반 안내 문구에 "use—세요 instead of—십시오 as an ending form"을 요구한다. EULA와 법률 문구만 '-십시오'를 유지한다.
- 카카오디벨로퍼스는 서술형 문장을 '-니다'로 끝내고 '하십시오'류 격식체와 '하세요'류 비격식체를 쓰지 않는다. 토스 앱인토스는 제품 문구에 "제품 안의 모든 문구는 '해요체'로 써요."를 적용한다.
- 공공언어 바로 쓰기는 '바람' 같은 명사형 종결이 권위적으로 읽히므로 '바랍니다'처럼 서술어 형태를 권한다.(인쇄 쪽 113) 스크립트: `(습니다|입니다)\.`와 `(해요|어요|예요)\.`의 혼용을 탐지한다.

개조식은 표와 짧은 지시 항목에만 쓴다. 카카오디벨로퍼스는 목록과 표 안에서만 개조식을 쓴다. 공공언어 바로 쓰기는 조사·어미·'-하다'의 과도한 생략을 금지한다.

조사와 띄어쓰기는 한글 맞춤법을 따른다.

- 한글 맞춤법 제41항: "조사는 그 앞말에 붙여 쓴다." 영문 식별자 뒤에도 같다. `API`가, `main.dart`를 처럼 공백을 두지 않는다. 스크립트: `[A-Za-z0-9\`] (은|는|이|가|을|를|의|에|로|와|과)`를 탐지한다. 조사 선택은 영어 발음에 맞춘다. 카카오엔터프라이즈 10계명의 2차 기사는 "영단어 뒤에도 영어 발음에 맞는 조사를 넣습니다."라고 적었다. 괄호 안 내용은 무시하고 괄호 앞 말 기준으로 고르며, 발음 사전이 필요하므로 사람이 판단한다.
- 자리표시자(`{0}`, `%s`) 뒤 조사는 은(는), 이(가), 을(를)처럼 이중으로 적는다. (Microsoft Korean Style Guide) 스크립트: `(\{\w+\}|%[sd])(은|는|이|가|을|를)(?!\()`를 탐지한다.
- 단위 명사는 띄어 쓰되 숫자 뒤에서는 붙여 쓸 수 있고(제43항), 전문 용어는 단어별 띄어쓰기가 원칙이되 붙여 쓸 수 있다.(제50항) 한 문서에서 한 방식으로 통일하고 용어집 표기를 Vale substitution으로 검사한다.
- '제-'는 접두사이므로 숫자와 붙여 쓴다.(제3조) (행정문서 표현 개선 보고서) 스크립트: `제 \d`를 탐지한다.
- 주어, 목적어, 필수 부사어를 생략하지 않는다. API 문서에서 누가 누구에게 무엇을 보내는지 빠지지 않게 쓴다. (10계명 2차 기사)

외래어는 외래어 표기법을 따른다.

- 제1항: "외래어는 국어의 현용 24 자모만으로 적는다." 제4항: 파열음 표기에 된소리를 쓰지 않는다. 어플리케이션은 애플리케이션, 비지니스는 비즈니스로 쓴다.
- 제5항: 굳어진 외래어는 관용을 존중하되 표기가 흔들리는 용어는 국립국어원 용례를 확인해 용어집에 고정한다. 린터: Vale substitution 사전(오표기 → 바른 표기).
- 원어는 한글 표기 바로 뒤 괄호에 쓴다. 소리가 같으면 소괄호 커피(coffee), 다르면 대괄호 국제 연합[United Nations]을 쓴다. 우리말로 바꿀 수 있는 외래어는 바꾼다. (행정문서 표현 개선 보고서; 법제처 정비기준)

문장 부호는 문장 부호 해설(2014)을 따른다.

- 쌍점: "쌍점은 앞말에 붙여 쓰고 뒷말과 띄어 쓰는 것이 원칙이다" 시:분, 장:절, 대비(65:60)만 앞뒤를 붙인다. 스크립트: `[가-힣] :`과 `:[가-힣]`을 탐지하고 숫자:숫자는 제외한다.
- 가운뎃점은 앞말과 뒷말에 붙여 쓴다. 열거를 일정 기준으로 묶을 때만 쓰고 단순 나열에는 쉼표를 쓴다. (한글 맞춤법 부록 제5항)
- 직접 인용에는 큰따옴표, 소제목·법률·규정 이름에는 작은따옴표를 쓴다. 영어 원문이 콜론으로 끝나도 '~합니다'로 끝나는 한국어 문장은 마침표로 끝낸다. (Microsoft Korean Style Guide 4.1.10)
- 자릿점 쉼표는 규정 밖이지만 쓰기로 했으면 일관되게 쓴다. 카카오디벨로퍼스는 4자리 이상 숫자에 3자리마다 쉼표를 쓴다.

숫자와 단위는 공공 문서 규정을 기준으로 한다.

- 숫자는 아라비아 숫자로 쓴다. (행정 효율과 협업 촉진에 관한 규정 제7조 제4항)
- 날짜는 `2022. 12. 31.`처럼 연월일 자리에 마침표를 찍고 마지막 '일' 뒤 마침표도 생략하지 않는다. 시각은 24시각제로 `15:20`처럼 쓴다. (행정업무운영 편람 부록; 문장 부호 해설 인쇄 쪽 10) 스크립트: `\d{4}\. ?\d{1,2}\. ?\d{1,2}(?![.\d])`와 `(오전|오후) ?\d{1,2}시`를 탐지한다.
- 수량은 숫자와 이상·이하·초과·미만으로 쓴다. '많은', '대량', '-등', '기타' 같은 불확실한 표현을 쓰지 않는다. (카카오디벨로퍼스) 린터: Vale existence 단어 목록.

번역투는 다음 패턴을 점검한다.

- '~에 의해 ~되다', '~에 있어서'를 바꾼다. 사물이나 추상 대상이 능동 주어가 되는 문장을 피한다. (공공언어 바로 쓰기 인쇄 쪽 12~13) 스크립트: `에 의해 .{0,10}(되|된|됨)`, `에 있어서`.
- 이중 피동 '보여지다', '되어지다'를 고치고 피동형과 사동형을 피해 행위 주체를 드러낸다. (법제처 정비기준; 카카오디벨로퍼스; hanlint)
- '명사 + 명사' 나열을 동사로 풀어 쓴다. (토스; hanlint `nounPile`)
- 단어 대 단어 직역을 피하고 필요하면 문장을 나눈다. (Microsoft Korean Style Guide 2.1.4)

한국어 자동 검사는 2026-11-02 기준 선택지가 좁다. textlint 공식 규칙 모음에는 Global, English, Japanese, Chinese, Arabic 절만 있고 한국어 전용 규칙은 없다. npm 검색 결과에도 한국어 전용 규칙은 없다. 일본어 기술문서 프리셋의 언어 독립 규칙(`sentence-length`, `max-comma`, `no-exclamation-question-mark`)만 재사용할 수 있다. hanlint는 `pip install hanlint` 뒤 `hanlint 글.md`로 번역투, 명사 나열, 이중 피동, 대상 없는 지시어를 잡는다. 지적이 있으면 종료 코드 1을 반환해 CI 게이트로 쓸 수 있다. hanlint는 2026-08에 만들어진 소규모 개인 저장소다. README의 한계 절은 "These checks do not judge truth, meaning or writing quality."라고 밝힌다. 맞춤법과 띄어쓰기의 나머지 영역은 사람 검토로 남겨 둔다.

## Markdown 문법과 린트 규칙

CommonMark는 표, 작업 목록, 각주를 핵심 문법으로 두지 않는다. "Because there is no unambiguous spec, implementations have diverged considerably." (John MacFarlane, CommonMark Spec 0.31.2) 렌더러가 확장을 지원하는지 확인하고, 불확실하면 제목, 목록, 펜스 코드, 링크만 쓴다. Write the Docs는 문서를 코드와 같은 도구로 다루라고 한다. 린터를 CI에 넣는 것 자체가 기준이다.

| 규칙 | markdownlint 또는 Vale/textlint 규칙 | 왜 가독성에 중요한가 | 출처 |
| --- | --- | --- | --- |
| H1은 하나, 첫 줄에 둔다 | MD025, MD041; remark `no-multiple-toplevel-headings` | 문서 주제가 하나임을 보여 주고 제목이 파일명과 일치한다 | Google Markdown style guide; Microsoft Learn; Standard Readme |
| 제목 레벨은 한 단계씩 내린다 | MD001; remark `heading-increment` | 건너뛴 레벨은 구조를 흐리고 보조기술 탐색을 깨뜨린다 | W3C WAI; GitHub Docs; markdownlint |
| ATX(`#`) 제목만 쓴다 | MD003 `atx` | Setext 혼용은 파서별 해석 차이를 드러낸다 | CommonMark; Ciro Santilli |
| 제목과 목록 앞뒤에 빈 줄을 둔다 | MD022, MD032 | 일부 파서는 빈 줄 없는 제목과 목록을 문단으로 처리한다 | markdownlint; Ciro Santilli; GitLab; SemBr |
| 제목 끝에 구두점을 쓰지 않는다 | MD026; remark `no-heading-punctuation` | 제목은 문장이 아니라 라벨이다 | Microsoft Writing Style Guide; remark preset |
| 같은 내용의 제목을 반복하지 않는다 | MD024(`siblings_only` 선택) | 중복 제목은 앵커를 깨뜨린다 | GitHub Docs; Write the Docs |
| 굵은 글씨를 제목 대신 쓰지 않는다 | MD036; remark `no-emphasis-as-heading` | 구조가 마크업에 없으면 탐색과 접근성이 사라진다 | WCAG 2.2 SC 1.3.1; Nielsen |
| 유형별 필수 제목을 고정한다 | MD043 `headings`(`*`, `+`, `?` 와일드카드) | 독자가 예상한 자리에서 정보를 찾는다 | Nygard; Standard Readme; Diátaxis reference |
| 줄 길이를 제한한다 | MD013(`line_length` 80 또는 100, 표·코드·제목 예외); remark `maximum-line-length` | 소스 편집과 diff 리뷰가 쉬워진다 | Google Markdown style guide 80자; GitLab 100자; SemBr 80자 |
| 글머리 기호는 `-`로 통일한다 | MD004 `dash`; remark `unordered-list-marker-style` | 기호 혼용은 소스 가독성을 떨어뜨린다 | Ciro Santilli; GitLab; 행정업무운영 편람 부록 |
| 번호 목록은 `1.` 반복 또는 오름차순 중 하나로 쓴다 | MD029 `one` 또는 `ordered` | 항목 재배치 시 번호 유지가 쉽다 | Google Markdown style guide; 행정 효율 규정 시행규칙 |
| 중첩 목록 들여쓰기를 고정한다 | MD007 `indent`, MD030 | 들여쓰기 불일치는 중첩 구조를 깨뜨린다 | Google Markdown style guide 4칸; 행정업무운영 편람 2타 |
| 코드 블록은 펜스(백틱)로 통일한다 | MD046 `fenced`, MD048 `backtick` | 들여쓰기 코드와 혼용하면 해석이 갈린다 | CommonMark; Ciro Santilli |
| 코드 블록에 언어를 지정한다 | MD040; remark `fenced-code-flag` | 구문 강조가 적용되고 복사 대상이 분명해진다 | Google Markdown style guide; Django; remark preset |
| 코드 블록과 표 앞뒤에 빈 줄을 둔다 | MD031, MD058 | 블록 경계가 분명해진다 | Standard Readme; markdownlint |
| 표의 열 수를 헤더와 맞추고 파이프 스타일을 통일한다 | MD056, MD055; remark `table-pipe-alignment` | 초과 셀은 렌더링에서 사라지고 소스에서 표가 표로 보인다 | markdownlint; GFM; GitLab |
| URL을 그대로 적지 않는다 | MD034; remark `no-literal-urls` | 설명 없는 링크는 훑어 읽기에 걸리지 않는다 | GFM; Google Markdown style guide |
| 링크 텍스트는 목적지를 설명한다 | MD059 `prohibited_texts` | 스크린리더가 링크를 맥락 없이 읽는다 | markdownlint; Google 스타일 가이드 |
| 빈 링크와 깨진 앵커를 두지 않는다 | MD042, MD051, MD052, MD053 | 깨진 링크는 문서 신뢰를 떨어뜨린다 | markdownlint; Standard Readme TOC |
| 이미지에 alt 텍스트를 넣는다 | MD045 | 시각 정보의 텍스트 등가물이 필요하다 | Google 스타일 가이드 접근성; W3C WAI |
| 인라인 HTML을 쓰지 않는다 | MD033 `allowed_elements` | 소스 가독성이 사라지고 GFM tagfilter가 일부 태그를 제거한다 | Microsoft Learn; GFM 6.11 |
| 고유명사 대소문자를 고정한다 | MD044 `names` | 표기 흔들림은 같은 대상을 다른 것으로 보이게 한다 | RFC 7322; markdownlint |
| 영문 문장 길이, 수동태, 군더더기를 검사한다 | Vale `Microsoft.SentenceLength`, `Google.Passive`, `write-good.Weasel`, `write-good.TooWordy`, `proselint.Needless`, `Google.WordList` | 긴 문장, 수동태, 기능 없는 단어가 가장 흔한 가독성 저하 요인이다 | Vale 패키지; GOV.UK; Google word list |
| 영문 제목 대소문자를 검사한다 | Vale `Google.Headings`(`$sentence`), `Microsoft.Headings` | 문장식 대소문자를 강제한다 | Vale Google 패키지 |
| 쉼표 수, 죽은 링크, TODO를 검사한다 | textlint `max-comma`, `no-dead-link`, `no-todo`, `terminology` | 언어 독립 규칙으로 Markdown에 바로 적용된다 | textlint |
| 한국어 번역투와 명사 나열을 검사한다 | hanlint `nounPile`, `cliche`, 이중 피동 | 한국어 전용 자동 검사의 현재 선택지다 | hanlint |

Vale는 "Vale is a command-line tool that brings code-like linting to prose."다. (docs.vale.sh) 규칙 파일 하나가 검사 하나이고 디렉터리가 스타일이다. 검사 유형은 existence, substitution, occurrence, repetition, consistency, conditional, capitalization, metric, readability, spelling, sequence, script 12종이다. textlint는 "textlint is an open source text linting utility written in JavaScript."이고 Markdown을 기본 지원한다. (textlint.org) remark 프리셋은 "You can use this package to check that markdown follows the Markdown Style Guide."라고 소개한다. 42개 규칙이 Ciro Santilli의 가이드를 코드화했다. (remark-preset-lint-markdown-style-guide)

바로 쓸 수 있는 `.markdownlint.jsonc` 예시다. MD026의 기본 구두점 목록에는 `?`가 없으므로 질문형 제목을 금지하려면 `punctuation`에 `?`를 추가한다.

```jsonc
{
  "default": true,
  "MD003": { "style": "atx" },
  "MD004": { "style": "dash" },
  "MD013": { "line_length": 100, "code_block_line_length": 80, "tables": false, "headings": false },
  "MD024": { "siblings_only": true },
  "MD029": { "style": "one" },
  "MD033": { "allowed_elements": [] },
  "MD044": { "names": ["Markdown", "GitHub", "GitLab", "JavaScript", "JSON"], "code_blocks": false },
  "MD046": { "style": "fenced" },
  "MD059": { "prohibited_texts": ["click here", "here", "link", "more", "여기", "이곳", "링크", "클릭"] }
}
```

최소 Vale 구성 스케치다.

```ini
# .vale.ini
StylesPath = .vale/styles
MinAlertLevel = suggestion
Packages = Microsoft, Google, write-good, proselint, alex, Readability

[*.md]
BasedOnStyles = Vale, Microsoft, write-good, alex
Microsoft.SentenceLength = warning
Google.Headings = YES
Readability.FleschKincaid = suggestion
```

한국어 용어 통일은 substitution 규칙으로 선언한다.

```yaml
# .vale/styles/Terms/Loanwords.yml
extends: substitution
message: "'%s' 대신 '%s'을(를) 쓴다"
level: warning
swap:
  어플리케이션: 애플리케이션
  비지니스: 비즈니스
  되어요: 돼요
```

## 측정과 한계

가독성 공식은 두 변수만 본다. DuBay는 어휘 난도와 평균 문장 길이가 텍스트 난도의 가장 좋은 예측 변수라고 정리했다. (연구, 인쇄 쪽 19) Flesch Reading Ease = 206.835 − 1.015 × (단어 ÷ 문장) − 84.6 × (음절 ÷ 단어)다. Gunning Fog = 0.4 × [(단어 ÷ 문장) + 100 × (3음절 이상 단어 ÷ 단어)]다. 넓은 독자 대상은 12 미만, 거의 모든 독자 대상은 8 미만을 목표로 한다. (Wikipedia 요약; Gunning 1952 원저 미열람) Vale Readability 패키지의 기본 임계값은 Flesch-Kincaid 8 초과, Flesch Reading Ease 70 미만, Gunning Fog 10 초과, Coleman-Liau 9 초과, ARI 8 초과, SMOG 10 초과, LIX 35 초과다. 문서 전체를 채점해 1행에 경고한다.

공식이 말하지 못하는 것이 더 많다.

- Flesch–Kincaid 계열은 "They neglect between-reader differences and effects of content, layout and retrieval aids." (Wikipedia, Flesch–Kincaid readability tests)
- DuBay는 "formula scores are better thought of as rough guides than as highly accurate values."라고 했다. (연구)
- Bailin & Grafstein은 긴 복문이 절 사이 관계를 명시해 "easier to understand than simpler sentences"일 수 있다고 주장했다. (연구, LINGUIST List 서평으로 확인)
- 짧은 문장 나열로 점수를 조작할 수 있으므로 점수를 합격 기준으로 쓰지 않는다. hanlint 같은 형식 검사도 글의 좋고 나쁨과 사실 여부는 판정하지 않는다.

Nielsen의 읽기 데이터는 분량 기준의 근거다.

- 1997년 실험에서 79%가 새 페이지를 스캔했고 16%만 단어 단위로 읽었다. 간결한 글은 사용성을 58%, 스캔 가능한 레이아웃은 47%, 둘과 객관적 어조를 합치면 124% 높였다. (연구)
- 2008년 데이터에서 사용자는 평균 방문 동안 페이지 단어의 "at most 28% of the words"를 읽고 현실적으로 20%만 읽는다. 단어 100개당 읽기 시간은 4.4초만 늘어난다. (Nielsen, How Little Do Users Read?) (연구)
- Rayner 외는 보통 성인의 읽기 속도를 약 250 wpm으로 보고 "there is a trade-off between speed and accuracy"라고 정리했다. (연구, 초록으로 확인) 단어 수 ÷ 250으로 예상 읽기 시간을 표기할 수 있다.
- GOV.UK는 이 데이터를 근거로 사용자가 20~28%만 읽는다고 안내한다.

분량 기준은 문서 유형별로 다르다. ADR은 1~2쪽(Nygard), 설계 문서는 큰 프로젝트 10~20쪽과 작은 문제 1~3쪽(Design Docs at Google), 종이 문서 대비 절반 이하 단어 수(Nielsen 1997)다. Ubl은 해법이 모호하지 않으면 설계 문서를 쓰지 않는다고 했다.

한국어에는 공인된 가독성 공식이 없다. 영어 공식은 음절과 단어 수에 의존하므로 한국어에 그대로 쓸 수 없다. Gunning fog 문서도 다른 언어에서는 정확하지 않을 수 있다고 적었다. WCAG 2.2 SC 3.1.5의 독해 수준도 한국어는 자동 측정이 불가능하다. 공공언어 바로 쓰기는 "문장을 적절한 길이로 작성하였는가?"를 요건으로 두지만 글자 수나 어절 수 기준값은 제시하지 않는다. 팀이 글자 수나 어절 수 임계값을 정하고 스크립트로 측정한 뒤, 판정은 사람이 한다. ISO 24495-1은 쉬운 글을 "Communication in which wording, structure and design are so clear that intended readers can easily" 찾고 이해하고 쓸 수 있는 글로 정의한다. (PLAIN 요약 페이지로 확인, 표준 본문 미열람) IBM의 Developing Quality Technical Information은 "apply nine essential characteristics of high-quality technical information"을 제안한다. accuracy, clarity, completeness, concreteness, organization, retrievability, style, task orientation, visual effectiveness다. (책, 서지만 확인) 이 아홉 축 가운데 린터가 보조하는 것은 style과 clarity 일부뿐이다.

## 가독성 체크리스트

Markdown 스펙 하나를 리뷰할 때 쓰는 목록이다. 괄호는 검사 방법, 화살표는 근거 절이다.

- [ ] (사람) 첫 단락에서 대상 독자와 범위를 밝혔다 → 제목과 구조
- [ ] (사람) 문서 유형을 하나로 정했고 다른 유형의 내용을 섞지 않았다 → 제목과 구조
- [ ] (사람) 결론과 핵심을 첫 두 단락에 두었다 → 제목과 구조
- [ ] (사람) 모든 문장이 생각 하나만 담는다 → 문장
- [ ] (린터) 영문 문장이 25단어를 넘지 않는다. `Microsoft.SentenceLength` → 문장
- [ ] (스크립트) 한국어 문장이 팀 임계값(글자 수·연결어미 수)을 넘지 않는다 → 문장
- [ ] (린터) 수동태와 이중 피동이 없다. `write-good.Passive`, hanlint → 문장
- [ ] (사람) 각 단락의 첫 문장이 주제문이다 → 단락과 절
- [ ] (스크립트) 단락이 5문장을 넘지 않는다 → 단락과 절
- [ ] (린터) H1이 하나이고 첫 줄에 있으며 제목 레벨을 건너뛰지 않았다. MD025, MD041, MD001 → Markdown 문법과 린트 규칙
- [ ] (사람) 제목만 읽어도 절 내용을 알 수 있고 범용 제목이 없다 → 제목과 구조
- [ ] (린터) 제목 끝 구두점과 중복 제목이 없다. MD026, MD024 → Markdown 문법과 린트 규칙
- [ ] (린터) 문서 유형의 필수 절이 순서대로 있다. MD043 → 제목과 구조
- [ ] (사람) 표는 2차원 데이터에만 썼고 항목 하나짜리 목록이 없다 → 목록·표·도식·코드
- [ ] (린터) 표에 헤더 행이 있고 열 수가 맞다. MD056 빈 셀 여부는 사람이 본다 → 목록·표·도식·코드
- [ ] (린터) 모든 코드 블록에 언어가 있다. MD040 → 목록·표·도식·코드
- [ ] (사람) 도식마다 제목, 범례, 단방향 라벨이 있고 색만으로 구분하지 않는다 → 목록·표·도식·코드
- [ ] (사람) 알림이 연속으로 없고 문서당 1~2개다 → 목록·표·도식·코드
- [ ] (린터) 링크 텍스트가 설명적이고 bare URL이 없으며 조각 링크와 alt가 유효하다. MD059, MD034, MD051, MD045 → 링크와 탐색
- [ ] (사람) '위에서', '아래', '앞서 설명한' 같은 방향·순서 의존 표현이 없다 → 링크와 탐색
- [ ] (린터) 용어와 고유명사 표기가 통일됐다. MD044, Vale substitution → 용어와 어조
- [ ] (사람) 약어를 첫 사용에서 풀어 썼고 문서당 3개 이하다 → 용어와 어조
- [ ] (린터) just, simply, easy, please 같은 군더더기가 없다. `Google.WordList` → 용어와 어조
