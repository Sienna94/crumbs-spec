# 개인 프로젝트 기획: 에이전트용 SPEC 문서 키트

2026-10-31 회사 Mac의 "호롤로" 세션에서 나눈 대화 중, 카페 프로젝트로 넘어가기 전까지의 내용을 정리했다.

## 1. 출발점

- 목표: GitHub에 올릴 에이전트 관련 개인 프로젝트. 일단 만들어 보고 공개 여부는 나중에 정한다.
- 1순위로 고른 주제: **에이전트용 SPEC 문서 키트 + 탐색 비용 벤치마크**
  - 회사에서 만든 SPEC 체계를 어느 저장소에나 적용할 수 있는 오픈소스 도구로 새로 만든다.
  - 차별점은 벤치마크다. "사람이 읽기 좋으면서 에이전트 탐색 시간을 줄인다"는 주장을 숫자로 증명한다. 경력기술서에서 가장 약한 부분이 이 수치다.
- 방향 결정: **"spec-kit에서 아쉬운 지점들을 개선한 버전"**으로 만든다.

### 같이 검토했던 다른 후보

| 순위 | 주제 | 판단 |
|---|---|---|
| 1 | 에이전트용 SPEC 문서 키트 + 탐색 비용 벤치마크 | 선택. 포트폴리오 주장을 직접 증명하고, MVP 2~3주, 모든 저장소에서 쓸 수 있음 |
| 2 | 자연어로 Flutter E2E(Patrol) 테스트를 만들고 고치는 에이전트 | 눈에 띄지만 시뮬레이터 환경 때문에 난이도와 데모 비용이 큼 |
| 3 | Flutter rebuild 경계 분석 에이전트 | 렌더링 최적화 경험과 연결되지만 분석 정확도를 보장하기 어려움 |

## 2. GitHub Spec Kit의 아쉬운 점

공식 문서와 사용자 후기에서 확인한 내용이다.

- **변경 단위 스펙만 다룬다.** 기능마다 디렉터리를 만들고, 그 안의 `spec.md`는 "이번에 바꿀 내용"만 담는다. 시스템 전체가 지금 어떻게 동작하는지 담은 문서는 없다.
- **기존 코드를 문서화하지 않는다.** 공식 가이드에 초기화가 "기존 동작의 스펙을 추론하지 않는다"고 적혀 있고, 시스템 전체 문서화는 권장하지 않는다. 이슈 #806에도 기존 프로젝트에서 반복 작업이 많다는 불만이 있다.
- **구현 이후 유지 방식은 팀에 맡긴다.** 기능 디렉터리를 이력으로 둘지, 살아 있는 문서로 계속 고칠지, 사후에 맞출지 세 가지 모델만 제시한다. `converge`는 지금 작업 중인 기능의 빈틈만 찾는다.
- **스펙 간 연결과 탐색이 없다.** 이미 배포된 기능의 스펙을 갱신하거나 스펙끼리 연결하는 명령이 레퍼런스에 없다.
- **산출물이 많다.** 변경 하나에 약 800줄이 나온다는 비교 후기가 있다. 2차 자료라 참고만 한다.

## 3. 개선 방향

| Spec Kit의 아쉬운 점 | 이 프로젝트의 개선 |
|---|---|
| 변경 단위 스펙만 있음 | **책임 단위의 살아 있는 문서.** 하나의 정책은 한 문서만 소유하고, 문서는 항상 "현재 시스템"을 설명한다 |
| 기존 코드 문서화를 지원하지 않음 | **`reverse` 명령.** 코드에서 현재 동작 초안을 만들고, 확인하지 못한 정책은 추정하지 않고 `[확인 필요]` 질문으로 남긴다 |
| 유지 방식을 팀에 맡김 | **드리프트 검사.** PR이 바꾼 사용자 결과를 기준으로 갱신이 빠진 문서를 찾는다(바뀐 파일 기준이 아님). 에이전트 지침에 "요청 없이도 갱신" 규칙을 넣는다 |
| 스펙 간 연결이 없음 | **링크 그래프.** 인덱스 → 개요 → 상세 → 관련 문서 구조와 역링크를 두고, 끊기면 `check`가 실패한다 |
| 산출물이 많음 | **사람 우선의 간결한 본문.** 식별자를 쓰지 않고, 탐색 정보는 링크로만 제공한다 |
| 효과를 측정하지 않음 | **탐색 비용 벤치마크.** Spec Kit 방식과 비교해 도구 호출 수, 토큰, 정답률을 측정한다 |

### Spec Kit과의 관계

- **이 도구는 Spec Kit 없이 혼자 동작한다.** 새 기능도 이 도구 안에서 처리한다.
- 새 기능 흐름: **분석 → 자료 요청 → 인터뷰 → 이해 내용 확인 → 책임 문서에 작성 → 검증.** Spec Kit의 specify → plan → tasks에 해당하는 단계가 이미 있다.
- 실제 차이는 문서를 두는 단위다.
  - Spec Kit: 기능을 만들 때마다 "이번 변경" 문서가 쌓인다.
  - 이 도구: 변경할 때마다 "현재 시스템" 문서를 고친다. 새 기능도 책임 문서를 새로 만들거나 기존 문서를 갱신한다.
- Spec Kit의 `specs/`를 옮겨 오는 `merge` 명령은 MVP에서 빼고, 필요하면 나중에 붙인다.

## 4. 구성 요소

- **`init`:** 문서 인덱스, 템플릿, `AGENTS.md` 규칙(지시 없는 갱신, 탐색 순서)을 생성한다.
- **`check`:** 검증 CLI. 인덱스에서 도달할 수 없는 문서, 역링크 누락, 깨진 anchor, 실존하지 않는 코드 경로, 정책 중복 소유를 검사한다.
- **에이전트 스킬:** writer, finder, interview 스킬을 Claude Code와 Codex 양쪽 형식으로 제공한다.
- **`reverse`:** 기존 코드에서 현재 동작 초안을 만들고 확인 질문을 남긴다.
- **`drift`:** PR diff가 바꾼 사용자 결과를 기준으로 갱신이 빠진 문서를 찾아 PR 코멘트로 알린다.
- **벤치마크:** 같은 질문을 SPEC이 없을 때, 식별자 방식일 때, 링크 그래프 방식일 때 각각 에이전트에게 시켜 도구 호출 수, 읽은 파일 수, 토큰, 정답률을 비교한다.

## 5. MVP 범위 (최종, 2~3주)

1. `init`, `check`: 템플릿, 에이전트 지침, 링크 그래프 검증
2. 새 기능 작성 흐름: 인터뷰 게이트와 writer 스킬
3. `reverse`: 기존 코드에서 초안을 만들고 확인 질문 남기기
4. `drift`: 갱신이 빠진 문서 찾기
5. 예제 앱 + 벤치마크 (직접 만든 작은 앱이나 오픈소스 앱 사용)

## 6. 정해 둔 조건

- **회사 자료는 쓰지 않는다.** 문서 구조와 규칙은 일반화해서 새로 쓰고, 회사 SPEC 문구, 검증 스크립트 코드, 도메인 용어는 옮기지 않는다.
- **이름:** `github/spec-kit`과 겹치지 않게 정한다. 프로젝트 이름은 `crumbs-spec`(npm 사용 가능 확인), 작업 폴더는 `~/crumbs-spec`, CLI 명령은 `crumbs`.
- **언어:** 별도 설치 없이 `npx`로 실행할 수 있는 Node.js(TypeScript)를 검토했다.
- **git:** 저장소 로컬 설정으로 `user.name "sienna"`, `user.email "siennachang.dev@gmail.com"`. Claude 공동 작성자 줄은 넣지 않는다.
- **원격:** `git@github.com:Sienna94/<저장소>.git` (SSH). 푸시는 허락할 때만.
- **작업 방식:** Opus가 구현 가이드 작성 → Haiku가 구현 → Opus가 검토.
